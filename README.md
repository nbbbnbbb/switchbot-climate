# Climate Log

SwitchBot温湿度計をGitHub Actionsで定期取得し、GitHub Pagesにグラフを公開します。サーバーの常時稼働やnpmのインストールは不要です。

## できること

- 複数センサーの温度・湿度を約2分ごとに記録
- スマートフォンに対応した1時間・6時間・24時間・7日・30日・90日のグラフ
- センサーごとの表示切替、最低・平均・最高、CSV出力、値の表表示
- 未接続・取得失敗・5分以上更新がない状態の表示
- 月別JSONによる長期履歴の保存（グラフ表示は直近90日まで）
- サンプル表示は明確に区別され、実際の記録に保存されません

## 初期設定

### 1. SwitchBotを準備

温湿度計をアカウントに登録し、対応するハブをインターネットへ接続してください。機種・アプリのバージョンに応じて「サードパーティーサービス」などの設定を確認します。

SwitchBotアプリ（v9以降）の「プロフィール → 設定 → アプリについて」でアプリのバージョンを10回タップし、「開発者向けオプション → トークンを取得」からTokenとSecretを確認します。表示名はアプリによって異なる場合があります。

### 2. GitHub Secretsを登録

リポジトリの **Settings → Secrets and variables → Actions → New repository secret** で登録します。キーはコードやIssue、チャットへ貼り付けず、Secretsの入力欄に直接登録してください。

| Secret | 内容 | 必須 |
| --- | --- | --- |
| `SWITCHBOT_TOKEN` | SwitchBotのToken | 必須 |
| `SWITCHBOT_SECRET` | SwitchBotのSecret | 必須 |
| `SWITCHBOT_DEVICES` | 取得対象と公開名を指定するJSON | 任意 |

`SWITCHBOT_DEVICES` を省略すると、対応する温湿度計を自動検出し、SwitchBotアプリ上の機器名で公開します。アプリで名前を変更すると次回取得時に表示名も更新され、過去の履歴は引き継ぎます。名前が空の場合のみ「センサー 1」などで表示します。検出できない機種や対象を限定したい場合は、次のJSONをこのSecretに登録してください。`name` は機器一覧に名前がない場合の予備名です。アプリの名前を優先します。`id` はSwitchBot APIの機器一覧 `GET /v1.1/devices` で確認する機器IDです。

```json
[
  {"id":"YOUR_DEVICE_ID","alias":"room-a","name":"展示室 A"},
  {"id":"YOUR_OTHER_DEVICE_ID","alias":"room-b","name":"展示室 B"}
]
```

`alias` は小文字英数字とハイフンで、一意かつ固定の名前にしてください。変更すると別センサーとして扱われます。自動検出から明示指定へ切り替える際は、`docs/data/latest.json` にある公開IDを `alias` に使うと履歴を引き継げます。自動検出時はSecretを使ったHMACで公開IDを作るため、Secretの変更でも公開IDが変わります。

**温湿度・取得日時・アプリ上の機器名（または明示設定した公開名）・履歴は、公開サイトとリポジトリから誰でも閲覧・ダウンロードできます。** 個人名や住所などを公開名に入れないでください。機器の実IDと認証情報は公開JSONに含めません。

### 3. GitHub Pagesを設定

**Settings → Pages → Build and deployment → Source → GitHub Actions** を選択します。

次に **Actions → Collect and publish climate → Run workflow → main → Run workflow** で収集を開始し、**Publish dashboard → Run workflow** で公開します。公開に成功した実行の `github-pages` environment に公開URLが表示されます。Secrets登録前に公開すると「未接続」の画面になります。

公開リポジトリでは標準GitHub-hosted runnerのActionsとPagesを利用できます。プランや利用規約はGitHub公式情報を確認してください。

## 動作

1. 同じGitHub Actionsランナーで約5時間40分、約2分ごとにSwitchBot API v1.1へ署名付きリクエストを送信します。セッション終了時には次の実行を予約し、別の5分間隔の監視処理が停止を検知して再起動します。
2. 認証情報と機器の実IDを取り除き、`docs/data/latest.json`、`status.json`、月別履歴と直近24時間の `live.json` を更新します。
3. データは取得ごとにGitへ保存します。Pagesの公開は別ワークフローで行い、ソース・共有設定の変更時と1日1回更新します。
4. ページは設定した間隔（既定1分）で再読込します。Pagesのデータが古い場合は公開リポジトリの最新保存データを直接読みます。ページを閉じても収集は継続します。

PCやスマートフォンの常時起動は不要です。GitHubの障害やランナーの起動待ちがあるため、厳密な間隔や無停止は保証されません。ページの日時は日本時間、保存データとCSVはUTCです。記録する日時はAPI取得時刻です。APIで同じ値が返っても記録します。API取得頻度と機器の測定・クラウド更新頻度は異なります。

失敗したセンサーは以前の値と取得時刻を残し、そのセンサーの新しい履歴は作りません。機器一覧の取得や設定検証が失敗した場合も既存値を保持します。長時間収集処理は次の周期で再試行します。必要な認証情報がない場合は起動を失敗させ、既存データを上書きしません。

表示中の期間について取得値の算術平均を計算します。時間加重平均ではないため、取得間隔に偏りがあると平均も影響を受けます。20分を超える空白はグラフの線を切ります。

2分間隔なら1台720回/日、自動検出を使うと機器一覧分としてさらに720回/日が必要です。温湿度計6台・ハブ1台・プラグ2台では計7,200回/日です。公式のAPI上限は1日10,000回です。他のアプリのAPI利用とリトライも考慮してください。取得間隔は `scripts/continuous_collect.py` の `INTERVAL`（120秒）で設定します。現在の台数で1分間隔にすると上限を超えるため、2分間隔を使います。遅延分をまとめて取り返す連続取得は行いません。手動実行の `samples` は旧バージョンとの互換用で、現在は長時間セッションを実行します。`continuous` をオフにすると、そのセッションの終了後に次のセッションを予約しません。
履歴は月別JSONとしてGitに保存し、現時点では自動削除しません。取得ごとにコミットするため、長期利用ではリポジトリが増大します。台数が多い場合や高頻度・長期運用ではデータベースへの移行を検討してください。収集を停止するときはActionsの画面でこのワークフローを無効化し、実行中の処理もキャンセルします。再開するときは有効化して手動実行します。

公開ページからSwitchBotへ直接アクセスする処理はありません。SwitchBotの認証情報はページに入力しません。共有設定を保存するときだけ、GitHubの書き込み認証を使います。

## 開発・検証

```bash
python3 -m unittest discover -s tests -v
node --test tests/*.test.mjs
python3 -m http.server 8000 --directory docs
```

`http://localhost:8000` で確認できます。外部のJavaScriptライブラリは使いません。フォントはGoogle Fontsから取得し、利用できない場合はシステムフォントで表示します。

実データの接続確認にはToken・Secretとオンラインのハブが必要です。自動テストはAPIの応答を模擬し、認証情報を含めません。

## グラフと共有設定

- グラフの線にカーソルを合わせると、その線のセンサー名・実際の取得値・取得時刻だけを大きく表示します。データのない空白を指しても値は補間しません。スマートフォンはタップ、キーボードはグラフにフォーカスして左右キーで取得値を確認できます。
- 「設定」から温度・湿度それぞれの最小値／最大値を個別に自動・手動へ切り替えられます。既定の期間・項目・表示センサー、点や線の表示、現在値カード・まとめ・表、画面更新間隔、空白と遅延判定の時間も設定できます。
- 設定の正本は `docs/settings.json` です。端末のローカル保存ではありません。全閲覧者は通常の画面更新で同じ設定を読み込みます。閲覧中の期間切替などは一時的な操作です。
- 設定画面の「変更をプレビュー」は未保存の設定を別タブで確認する機能です。他の閲覧者へは反映しません。
- 「共有設定を保存」は、このリポジトリのみを対象にContentsのRead and write権限を持つGitHub Fine-grained personal access tokenで認証し、GitHub Contents APIへ書き込みます。トークンはブラウザー保存領域や設定JSONへ保存しません。GitHubのログインCookieやSwitchBotのToken・Secretを代用することはできません。
- 保存時は設定ファイルのSHAで競合を検知します。競合した場合は再読込して変更を確認してください。収集処理は保存前に最新mainへ追従するため、設定更新とデータ保存が別ファイルでも継続でき、次の公開時に全体設定が反映されます。
- 保存後の公開反映は通常は次の収集・公開時です。開いているグラフは、その後の画面更新で設定を読み直します。GitHubの書き込み認証を用意できない場合は、GitHub上の `docs/settings.json` を直接編集する方法もあります。


## 立体ヒートマップと配置

- 床面の三角形 A=(0,0)、B=(幅,0)、C=(頂点X,奥行)を高さ方向へ押し出した三角柱です。設定画面で寸法（m）を編集します。初期の幅2 m・奥行2 m・高さ2.4 mは仮の値で、写真からの実測ではありません。
- センサーの実際の位置は初期設定に含めません。平面図でX/Y、正面図でX/Zをクリック・ドラッグするか、数値欄から室内外へ配置します。矢印キーでも調整できます。配置は `sensorPositions` に公開IDをキーとして保存します。
- 3D表示はドラッグと矢印キーで回転、ボタンで拡大・縮小できます。室内の推定分布を立体の表面に表示します。点の横にアプリのセンサー名と実測値を表示し、下の一覧も実測値、面の色は空間補間による推定値です。
- 室内かつ補間対象として有効にした測定点だけで、3D距離の逆数による重み付き平均（IDW、既定の指数2）を計算します。室外の点・無効な点・欠測値は補間から除外します。値は測定値の最小〜最大内に収まり、測定点位置ではその値になります。同じ位置のセンサーは平均します。1台では一様色となり、その旨を表示します。
- 温度と湿度は3D表示上のタブで切り替えます。温度・湿度の時系列グラフは常に並列（狭い画面では上下）に表示します。
- 時間スライダーは選択期間内の実際の取得時刻を選びます。未来の値を先取りせず、選択時刻までの最新の有効値を使います。有効時間（既定5分）を超えた値は欠測です。再生、前後の取得時刻、最新へ戻る、再生速度を操作できます。
- ヒートマップの温度・湿度それぞれに、グラフとは独立した最小/最大/自動、最小・中間・最大の色、中間色の割合を共有設定できます。自動範囲は選択期間の有効な室内センサーの記録から決めて再生中は固定します。範囲外は端の色で表示します。
- 空気の流れ・断熱・壁の影響は計算しません。測定点のない場所、とくに測定点に囲まれていない領域には不確かさがあります。空間全体の実測やCFDではありません。
- 現在の配置をすべての履歴に適用します。センサー移動の履歴は保存しません。過去の配置を再現したい場合は元の配置へ戻してプレビューします。
- 寸法・配置・配色も既存の共有設定と同じ保存経路で、保存後は全閲覧者へ適用します。プレビューは保存せずに確認できます。既存の軸範囲・表示センサーなどはそのまま引き継ぎます。


## ページ配置と時間軸

温度・湿度の並列グラフをページ上部に置き、その下に3Dヒートマップを表示します。グラフ上部の1時間・6時間・24時間・7日間・30日間・90日間で、グラフとヒートマップの表示期間を同時に切り替えます。3D表示は表面だけを使い、高さ断面は表示しません。

時系列グラフの縦グリッドは日本時間の毎時00分と30分に揃え、正時を強調します。時刻ラベルは表示幅と期間に応じて間引き、長い期間では日付も付けます。表示範囲の端や現在時刻に合わせた半端な分の目盛りは作りません。


## 取得対象と消費電力表示

- CO₂機器（MeterPro(CO2)など）と旧CO₂公開IDは取得対象から除外します。機器一覧に含まれていてもステータスAPIを呼ばず、最新値・グラフ・配置選択には表示しません。過去の記録は履歴ファイルに保持します。
- 「ハブミニ 22」（Hub Mini2）は表示・配置対象から除外します。取得処理と既存履歴は保持します。現時点の実機確認ではステータスAPIが空オブジェクトを返すため、未取得と明示します。温湿度が返るようになれば履歴へ記録します。0や他センサーの値を代用しません。Webhookを使う場合は、GitHub Pagesとは別の受信サーバーが必要です。
- 「プラグミニ A」「プラグミニ B」（Plug Mini JP）のON／OFFと消費電力を取得します。名前の空白や英数の全半角を正規化して選択し、表示にはアプリの元の名前に、Aは「除湿機」、Bは「加湿機」の説明を加えます。プラグへの電源操作は行いません。
- プラグの履歴は各行の `plugs` に `power`（on/off）と `powerWatts`（W）を保存し、温湿度の `values` と分けます。0 WでもONの機器はONのまま保存します。失敗時は取得時刻を進めず、履歴を作りません。
- 湿度の下に、時間軸と左右の余白をそろえた独立した消費電力グラフ（W）を表示します。高さは湿度グラフの約3分の1です。その下の番号付き帯がプラグごとの状態です。濃い帯がON、薄い帯がOFF、空白が未取得です。状態は取得時点から次の取得、または最大5分まで表示し、長い欠測を埋めません。線・帯を指すと1台の取得値と日時を表示します。
- 設定画面で電力線と状態帯の表示、表示するプラグ、W軸の最大値（自動／手動）を全閲覧者共通で保存できます。通常画面のプラグチェックは閲覧中だけの切り替えです。現在値カードにも状態・W・取得時刻を表示します。温湿度CSVには温湿度センサーだけを出力します。


## 収集の継続と自動復旧

- 収集は `continuous_collect.py` が同じランナー上で約5時間40分継続し、約2分ごとに最新値・履歴・`docs/data/live.json` を保存します。処理に90秒の上限を設け、失敗時は前回の測定日時を維持して次の周期で再試行します。
- 保存が競合した場合は最新のmainへ未保存の取得行だけを再適用します。履歴全体を古いコピーで置き換えず、保存成功まで取得行をメモリに保持します。
- 終了時は次の長時間セッションを起動します。独立した監視ワークフローも5分ごとに状態を確認し、停止時は起動、実行中の処理が10分以上進まない場合は再起動します。ランナー待ちを実行中のハングと取り違えて、待ち行列を増やすことはしません。
- Pagesの公開と収集を分離しました。ソース・共有設定の変更時と1日1回はPagesを公開します。表示側は公開データが2分以上古いとき、公開リポジトリの `live.json` をContents APIまたはrawエンドポイントから読みます。API呼び出しは90秒に1回までに制限し、直近24時間は1回の取得で値と履歴をまとめて受け取ります。長期間の履歴もリポジトリから読みます。
- 通信にはタイムアウトを設け、オンライン復帰・ページ復帰時にも自動で読み直します。
- GitHub Actions・Pages・REST APIすべてに及ぶ障害やSwitchBot側の停止まで無停止を保証するものではありません。GitHub公式の障害情報は https://www.githubstatus.com/ を参照してください。完全に独立した取得経路が必要な場合は、別事業者の定期実行基盤または常時稼働するローカル収集機が必要です。
